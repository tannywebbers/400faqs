================================================================================
 PHASE 15 — FINAL PRODUCT INTEGRATION & MONETIZATION COMPLETION
================================================================================

This document records the Phase 15 audit and completion of the 400QUES monorepo
(packages/db, apps/api, apps/web). Phase 15 is the final integration phase that
verifies the whole product is wired end-to-end, re-using the existing
implementation from earlier phases rather than rebuilding it.

--------------------------------------------------------------------
1. WHAT WAS AUDITED (Phase 15 checklist)
--------------------------------------------------------------------

The checklist subsystems were verified present, wired, and internally
consistent. This phase did NOT rebuild any of them — it audited, swept for
stale references, verified configuration completeness, captured the pending
database migrations, and re-confirmed type safety.

A. PUBLIC WEBSITE ................................................. PRESENT
   - apps/web/src/app/(public): home, categories, category detail, contribute
     (anonymous), monetize gate page, report, request-category, help (+article),
     about, privacy, terms, contact, search, status.
   - Backed by apps/api/src/routes/public.ts: /settings (public-safe),
     /categories, /questions, /contributions (comment status lookup),
     /reports, /category-requests, /ads/meta, /ads/placement/:placement,
     /ads/events. Rate-limited (publicLimiter / contributionLimiter).

B. ANONYMOUS CONTRIBUTION + GOOGLE AI DUPLICATE DETECTION + MODERATION ... PRESENT
   - Public POST /contributions accepts userPhone as optional/nullable
     (z.string().min(8).max(20).optional().nullable()), and userId is resolved
     only when a matching phone exists → anonymous submissions are first-class.
   - Duplicate detection (question-similarity.ts) is Google AI: reads
     GOOGLE_AI_API_KEY / GOOGLE_AI_MODEL / GOOGLE_AI_ENDPOINT /
     GOOGLE_AI_TIMEOUT_MS from config (server-only env, never exposed), calls
     the generative-language :generateContent endpoint, returns
     EXACT_DUPLICATE / VERY_SIMILAR / UNIQUE with strict-JSON output parsing,
     AbortController timeout, and a safe manual-review fallback when AI is
     disabled/unavailable/malformed (never auto-approves on guesswork).
   - Content moderation (lib/ai.ts): deterministic heuristics always run; an
     LLM enrichment is best-effort and key-gated. Exact duplicates are rejected;
     very-similar/lower-confidence routed to pending manual review; disallowed
     content is flagged. Admin settings control thresholds and auto-approve.
   - Admin review (routes/admin/contributions.ts) re-checks for exact
     duplicates at final approval (isExactDuplicateAtApproval).

C. WHATSAPP BOT / WEBHOOK / ADMIN + META TEMPLATE SYNC .............. PRESENT
   - App webhook (admin/webhook + webhook.ts) audited in Phase 14: GET
     verification + POST with mandatory HMAC-SHA256 raw-body signature check,
     immediate {received:true}, idempotent processedEvent/P2002 processing,
     game flow (START aliases), gate pause/resume, production workers and
     recovery jobs. All carried forward untouched.
   - WhatsApp admin (routes/admin/whatsapp.ts) is complete: /status (returns
     botNumber, publicStartLink https://wa.me/<digits>?text=START,
     monetizationEnabled, connection, stats, webhookUrl), /config CRUD with
     masked secrets, /webhook + token regeneration, /templates (read-only list),
     /templates/sync (Meta read-only sync — Meta remains the source of truth;
     NO local create/edit/submit/approval), /messages logs, /sessions, /stats,
     /test-send. All admin actions audit-logged and JWT/role protected.
   - Frontend: apps/web/src/app/admin/whatsapp 6-tab console incl. the
     "Player Entry Point" card (bot number, monetization on/off, copyable START
     link) added in Phase 14.

D. MONETIZATION GATE + PROVIDER-AGNOSTIC ADAPTER + AD PROVIDER ADMIN ... PRESENT
   - apps/api/src/services/adproviders/* (types/registry/serve/callbacks/index):
     generic adapters (SCRIPT, DIRECT_LINK, REDIRECT, SNIPPET, API, CPA,
     VERIFICATION, OTHER). Application never branches on a vendor — it asks the
     adapter "which enabled provider serves this placement?"
   - Placement serving is driven by the AdPlacement table (servePlacement):
     an enabled placement assigned to an enabled/non-archived provider. Priority
     or random rotation. Estimates recorded via recordEvent.
   - selectAdsForGate resolves the WhatsApp gate provider through placement
     keys WHATSAPP_VERIFICATION / GATE (with default-provider and gate-serving
     fallbacks). Game rules/START flow unchanged.
   - Admin ads console (routes/admin/ads.ts + apps/web/src/app/admin/ads 3-tab):
     manage providers (types, enable/disable, archive, priority, per-placement
     assignment, providerPlacementId, format), placements, snippets, validate a
     provider's configured fields, view revenue — disable without deleting
     history, never exposes secrets.
   - Callbacks (routes/callbacks.ts POST /api/webhooks/ads/:providerId) verify
     provider callback secret/HMAC before attributing events.

E. AD PROVIDER REVENUE CONFIG + PLACEMENTS ......................... PRESENT
   - AdProvider carries revenueModel (CPM/CPC/CPA/FIXED), currency,
     cpmRate/cpcRate/cpaRate/fixedPayoutPerVerification, and the per-unit
     estimatedPayout* fields. (Schema + migrate-diff baseline confirmed.)
   - recordProviderChannelRevenue maps IMPRESSION→CPM and CLICK→CPC to ESTIMATED
     revenue rows; CPA/FIXED defer to verification/conversion callbacks.

F. REVENUELEDGER (ESTIMATED vs CONFIRMED vs PAID TRUST MODEL) ....... PRESENT
   - AUTO rows on completed verification (idempotent per gate) recorded as
     isEstimated=true pending; MANUAL rows by admins; updateLedgerStatus lifts
     rows to confirmed/paid (clearing isEstimated + setting confirmedAt); stats
     separate estimated vs confirmed vs paid; CSV export; provider-channel
     estimates clearly labelled and only elevated through official callbacks or
     admin confirmation. No fabricated CONFIRMED revenue.

G. FLOATING START BUTTON + PUBLIC SETTINGS + ANALYTICS + WORKERS .... PRESENT
   - whatsapp-float.tsx + use-public-settings reads whatsapp.number (public).
   - getPublicSettings (cached, public-only) powers the public site.
   - Admin analytics, daily AnalyticsSnapshot, Redis-backed workers/crons
     (game.worker, notification.worker, recovery) with distributed locks, and
     audit logging all present and type-checked.

H. NO-STALE CODE SWEEP ........................................... CLEAN
   - grep of apps/api + apps/web for campaign/broadcast/badge/leaderboard/
     publicProfile/displayName found NO dead application references. The only
     remaining mentions are the orphaned DB models (Badge, UserBadge, Campaign,
     CampaignDelivery) and reserved enum values (AD, BROADCAST,
     CAMPAIGN_COMPLETED). Per policy these are left orphaned and NOT dropped
     (destructive migration is out of scope for a build-only phase).
   - No hard-coded vendor ad logic anywhere (Adsterra/PropellerAds/Google only
     appear in generic comments/examples inside the provider-agnostic layer).
