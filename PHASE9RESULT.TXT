What was built:

1. GOOGLE AI DUPLICATE DETECTION (MANDATORY)
   New dedicated service: apps/api/src/services/question-similarity.ts
   - Candidate search in the DB FIRST (same category, prefer same type; top
     maxCandidates ranked by a local Jaccard+distance heuristic), then send only those
     candidates to Google AI for classification — cheap, fast, and private.
   - Google AI structured-JSON output (temperature 0, responseMimeType application/json):
       { "classification": "EXACT_DUPLICATE" | "VERY_SIMILAR" | "UNIQUE",
         "confidence": 0..1, "matchScore": 0..1,
         "matches": [{ "questionId", "similarity", "reason" }] }
   - No new npm dependency: the API talks to the official Google REST endpoint
     https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent with
     header x-goog-api-key, generationConfig temperature 0 + responseMimeType json, and an
     AbortController timeout. The key is env-only (GOOGLE_AI_API_KEY) — never stored in the
     DB, never returned in any API response or WhatsApp message.
   - Decision matrix (apps/api/src/services/moderation.ts):
       * Deterministic normalized exact match (strip punctuation/case/spaces) -> REJECTED
         (auto, stored duplicateOfId) — never relies on AI being reachable.
       * AI EXACT_DUPLICATE with confidence >= exactThreshold -> REJECTED.
       * VERY_SIMILAR with score >= similarThreshold -> PENDING manual review (admins
         notified, friendly reviewReason stored in aiResult).
       * UNIQUE -> APPROVED when auto-approve is ON; otherwise PENDING.
       * AI unavailable / malformed / error -> safe fallback: PENDING review with a
         friendly reviewReason. The pipeline NEVER auto-approves when review is required
         and NEVER leaks AI/credential error details to the user.
   - "PENDING_REVIEW" is mapped to the existing ContributionStatus.PENDING (no new enums).
   - Admin approve path re-checks exact duplicates via recheckDuplicateBeforeApproval()
     (race + manual-override guard) and always assigns a question number via
     createApprovedQuestion() (3-attempt retry on the P2002 unique(number, categoryId)
     conflict, increments category.questionCount). Pre-existing bug fixed: the old admin
     approve flow created questions WITHOUT a number.
   - OpenAI moderation (lib/ai.ts moderateContent) is KEPT for content moderation; only
     duplicate detection moved to Google AI. Old OpenAI checkDuplicates is no longer used.

4. BACKEND ROUTES
   Public (apps/api/src/routes/public.ts):
   - GET  /api/public/categories/:slug/questions — paginated category questions with
     q / type / difficulty / sort (newest|plays) + category meta (incl. gameType).
   - POST /api/public/contributions — submits through the full AI pipeline (type-aware:
     TRUTH_DARE categories accept only TRUTH/DARE, default TRUTH when omitted; NORMAL
     categories accept only NORMAL).
   - GET  /api/public/contributions?phone (status filter, paginated, includes category,
     duplicateOf text, and Google AI classification).
   - GET  /api/public/contributions/:ticket — now returns type + classification + aiResult.
   - GET  /api/public/reports?phone (status filter, paginated, includes category/question/
     screenshot/resolution).
   - GET  /api/public/category-requests?phone (status filter, paginated, includes note reply).
   - GET  /api/public/profile?phone — user stats (sessions/answered/asked), badges,
     contribution/report/categoryRequest counts, and recent activity; phone masked.
   - GET  /api/public/categories (list) + /api/public/categories/:slug (detail) now expose
     gameType (needed by the /app contribute form). Leaderboard/top-contributors trusted:
     phones are masked server-side (leaderboard is aggregate-approved counts).
   Admin (apps/api/src/routes/admin/contributions.ts): APPROVE performs the exact-dup
   recheck, then createApprovedQuestion + badge awarding + audit log ("APPROVE"); REJECT
   writes audit "REJECT" with a reason. Removed the bogus userBadge.upsert (badgeId "") no-op.
   Identities are phone-based; every history/profile route requires the phone param and
   only ever returns that phone's own records (no cross-user data), with masking applied.
