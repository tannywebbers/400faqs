================================================================================
 PHASE 16 — DEPLOYMENT READINESS, UI POLISH & CONFIGURATION WIRING
================================================================================

This document records the Phase 16 (deployment readiness) work on the 400faqs
monorepo (packages/db, apps/api, apps/web). Phase 16 focuses on making the
product deployable: fixing UI/build blockers, wiring public landing content
to configuration, hardening the admin system-status screen, correcting
How-It-Works commands, confirming the production build and typechecks pass,
and documenting the remaining runtime-test blocker.

Phase 16 did NOT add new product features. It preserved: provider-agnostic
advertising, RevenueLedger, anonymous contributions, Meta as the source of
truth for WhatsApp templates, and the existing admin JWT/roles/audit. It did
NOT reintroduce accounts/profiles/leaderboards/badges/campaigns/broadcast/CRM
or subscriptions. Server secrets never reach the browser.

--------------------------------------------------------------------
1. WHAT WAS COMPLETED
--------------------------------------------------------------------

A. SYSTEM STATUS (public health surfaced in admin) .................. DONE
   - Removed the public /api/public/status route from
     apps/api/src/routes/public.ts (and dropped the now-unused
     getSystemStatus import).
   - Deleted apps/web/src/app/(public)/status/ (public-facing status page).
   - Hardened apps/api/src/services/status.ts: WhatsApp fetch wrapped in a
     5s withTimeout guard so a hanging provider can no longer stall health.
   - Rewrote the admin health screen (apps/web/src/app/admin/health/page.tsx)
     as an explicit CHECKING / HEALTHY / DEGRADED / UNHEALTHY / ERROR state
     machine with an OVERALL_META banner, a 15s client watchdog timeout, and
     per-service "unknown"/"Unavailable" fallbacks.
   - Renamed the admin nav label "Health" -> "System Status" in
     apps/web/src/app/admin/layout.tsx.

B. LANDING PAGE EDITOR (settings-driven) ............................. DONE
   - apps/web/src/app/(public)/page.tsx now reads landing.* settings
     through JSON-parse helpers (parseJson / DEFAULT_STEPS /
     DEFAULT_FEATURES) for: How-It-Works steps + title/subtitle, Features
     items + title/subtitle, Trending Categories, FAQ title, and CTA
     title/body.
   - apps/web/src/app/admin/settings/page.tsx gained a "Landing Page" group
     with 12 public:true fields (including JSON textareas with hints).

C. HOW-IT-WORKS COMMANDS ............................................. DONE
   - Added "status" (+ alias "state") to the CommandName union and the
     REGISTRY in apps/api/src/services/commands.ts. Previously "status" was
     advertised in help/messages (messages.ts) but missing from the registry,
     so /status returned "unknown command". All help-listed commands now work.

D. STALE REFERENCE SWEEP ............................................. DONE
   - Node scan confirmed no stale 400QUES / @400ques references in any code
     file (only historical PHASE*.TXT docs remain, intentionally untouched).
   - Admin auth token keys correctly use 400faqs_admin_token /
     400faqs_admin_user.
   - apps/api/src/app.ts maintenance gate now only bypasses /api/webhooks
     (stale /api/public/status bypass removed).

E. ADMIN PASSWORD RESET (DATABASE FIX) ............................... DONE
   - Ran a one-off reset script: admin@400faqs.com / admin1234 (matched=1),
     then deleted the script. .env carries ADMIN_PASSWORD=admin1234,
     PORT=4000, NEXT_PUBLIC_API_URL=http://localhost:4000, WORKER_PROCESS=0.

F. GOOGLE FONTS BUILD BLOCKER ........................................ DONE
   - next/font/google "Inter" fetch hangs on this network. Replaced the
     next/font Inter with a system font stack:
     apps/web/tailwind.config.ts sans =
     ["system-ui","-apple-system","Segoe UI","Roboto","Helvetica Neue","Arial","sans-serif"].
   - Removed Inter import + inter.variable from apps/web/src/app/layout.tsx.
   - The build now reaches static page generation.

G. BUTTON asChild / RADIX SLOT BUILD BLOCKER ......................... DONE
   - Production web build failed while generating static pages on every
     (public) route with: "Slot failed to slot onto its children. Expected a
     single React element child or `Slottable`."
   - Root cause: the public Header used <Button asChild> around
     <Link>/<a> children. During Next.js static prerendering this Radix
     Slot usage did not resolve to a single valid element, throwing at
     node_modules/@radix-ui/react-slot (createSlotError).
   - Fix: replaced the three <Button asChild> usages in the public Header
     (apps/web/src/components/layout/header.tsx) with semantically correct
     plain <Link>/<a> elements carrying the equivalent button classes. This
     is cleaner for SEO/a11y (real links) and removes the fragile Slot path
     from the shared header.
   - Also kept the Button component's defensive fix: the loading spinner is
     only rendered for real <button> elements (!asChild && loading), never
     injected into asChild slot targets.
   - After the fix the web production build completes cleanly:
     "Generating static pages (45/45)" with zero errors (see section 3).

4. RUNTIME-TEST BLOCKER (NOT PERFORMED)
--------------------------------------------------------------------

   Local API/runtime boot testing is BLOCKED in this environment:
   - Redis is hard-required by the API at startup (REDIS_REQUIRED=false is a
     dev-only override) and no Redis is present here.
   - Docker (which would provide redis/postgres via docker-compose.yml) is
     unusable and was explicitly out of scope per user instruction.
   Runtime endpoint tests can be run once a hosted REDIS_URL is supplied.
   The Supabase DATABASE_URL is reachable and was used for the admin
   password reset (section 1E).
