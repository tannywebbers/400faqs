IMPLEMENTATION SUMMARY
----------------------
Phase 11 (analytics build-out) was carried out on the completed 400QUES monorepo
(packages/db, apps/api, apps/web) and delivered a full admin BI surface on top of the existing
product while keeping every constraint (build-only, no new dependencies, no runtime testing):

  - A new analytics service suite (apps/api/src/services/analytics-advanced.ts) with DB-aggregated
    BI for platform overview, users, sessions, contributions, AI screening, WhatsApp messaging,
    monetization (8-step verification funnel), revenue (ESTIMATED vs CONFIRMED), daily timeseries,
    top questions/leaders, question analytics, and category rankings — every response masks phone
    numbers and is bounded (no whole-table loads).
  - A revenue trust model: ESTIMATED revenue is computed on read from real activity x admin-entered
    provider rates (never auto-written as real money); CONFIRMED revenue comes only from confirmed
    RevenueLedger rows; automations create ledger rows with eventType=VERIFICATION and
    isEstimated=true; every ledger row tracks eventType, estimate flag, recordedAt, confirmedAt,
    and the creating admin (createdById).
  - Extended revenue + monetization admin APIs: manual ledger entries now record eventType /
    estimate flag / recorded-at / metadata / creating admin; ad-provider admin CRUD now manages
    revenue model (CPM/CPC/CPA/FIXED), currency, CPM/CPC/CPA rates, fixed payout per verification,
    and per-event estimated payouts with audit on every settings change.
  - 13 new /api/admin/analytics/* endpoints and a dataset-aware CSV export that keeps the legacy
    overview export byte-compatible (dataset=overview) while adding revenue/monetization/
    contributions/sessions/users/questions/ai/whatsapp raw exports.
  - The /admin/analytics page was rewritten as a 10-tab BI dashboard (Overview, Users, Sessions,
    Content, Contributions, AI, WhatsApp, Monetization, Revenue, Categories) with preset + custom
    date ranges, KPI grids with trend badges, recharts (line/bar/area), an 8-step monetization
    funnel, category rankings, snapshot capture, and dataset-aware CSV export.
  - The /admin dashboard now shows trailing-30d revenue quick stats (estimated/confirmed/total/paid)
    and a "View Analytics" button.
  - TypeScript typecheck passes with 0 errors for all three packages (db, api, web). A strict
    BUILD-ONLY approach was followed: no tests, no servers, no runtime/WhatsApp/Google-AI/live-DB
    verification. Lint was not run because the repo has no ESLint configuration (pre-existing).

BUGS / FUNCTIONALITY FIXED
--------------------------
  1. Gate total precedence bug (analytics-advanced.ts overviewBag + monetization gateCreated):
     `?? 0` combined with additions for other status counts without parentheses collapsed the
     "all gates / gates created" totals, so KPIs could be wrong whenever a status bucket was null.
     Fixed by wrapping every `?? 0` term in explicit parentheses.
  2. revenue.ts: `input.isEstimated ?? (status !== "confirmed" && status !== "paid")` — `??` and
     `&&` mix-up could compute the estimate flag incorrectly; broken out with explicit parens and a
     RevenueEventType import/cast for eventType normalization.
  3. Removed a `p.lastName ??=` mutation loop that could corrupt the phone->player aggregation map.
  4. Removed a dead gateProvider map and a pointless `for (const row of statusGroup.slice()) void row;`
     (no-op leftover).
  5. frontend applyCalendar: reassigning a `const start` in the YTD branch (TS2588) -> now `let`.
  6. frontend preset buttons: a convoluted mixed-type highlight condition (TS2367) and the presets
     were reworked to a {key,label,run} list with an explicit activeKey; leftover activeRange state
     removed.
  7. CSV export dataset mismatch: the UI offered a "WhatsApp" export but renderAnalyticsCsv had no
     whatsapp case (silently fell back to the overview series); a WhatsApp message-log export case
     was added (date/direction/phone/type/status/template/WA message/content/error).

IMPORTANT ARCHITECTURAL DECISIONS
---------------------------------
  (All inherited Phase 1-10 product decisions remain in force; no game/economy behavior changed.)
  NEW decisions:
    - Revenue is never fabricated: ESTIMATED = real activity x admin rates, computed on read, never
      auto-written; only admins confirm entries, and a confirmed/paid ledger row is the single
      source of CONFIRMED revenue. Totals keep separate estimated, confirmed, total and paid views.
    - AI cost can't be tracked without a token feed, so the UI/API say so explicitly instead of
      guessing; monetization providers' estimated payouts stay admin inputs.
    - All BI queries use DB aggregation (groupBy/count/raw where available) with bounded takes and
      masked phones; no endpoint loads an unbounded table into memory.
    - The new analytics stack is additive and gated: analytics.enabled keeps every endpoint
      answerable but silent when disabled; the legacy analytics behavior (snapshots, overview CSV,
      base endpoints) is preserved byte-for-byte.
    - Provider-level revenue estimates live with the provider row (audited on change) so the BI can
      attribute estimated revenue per provider/event without inventing truth.
    - Everything new is admin-only; public API surface and webhook remain unchanged.
    - No new npm dependencies were added in this phase.
