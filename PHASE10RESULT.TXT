2. MARKETING CAMPAIGNS (bulk WhatsApp with rate limiting + delivery tracking)
   New Campaign + CampaignDelivery models and apps/api/src/services/campaign.ts, worker
   apps/api/src/workers/campaign.worker.ts, and the "campaign" BullMQ queue.
   - Lifecycle: DRAFT -> SCHEDULED/RUNNING -> PAUSED -> resumed -> COMPLETED/CANCELLED.
     Audiences: all_users, active_users (lastActiveDays), players (minSessions +
     lastActiveDays), contributors (minContributions), specific_users (phones CSV),
     seed_invites (creators of WAITING sessions). Audience resolution caps at
     campaign.maxRecipients. POST /audience/preview resolves a live count + sample before
     creating a campaign.
   - Scheduling: "now", "scheduled" (scheduledAt) or "recurring" (5-field cron). A single
     concurrent cron (1-minute, dynamic import advanceDueCampaigns) promotes due SCHEDULED
     campaigns to RUNNING when campaign.autoProcess is enabled. recurring runs compute the
     next run with nextCronRun and re-arm themselves after each completion.
   - Dispatch: startCampaign resolves recipients into CampaignDelivery rows (queued) then
     enqueues a "dispatch" job. processCampaignBatch sends up to rateLimitPerMinute
     messages, then re-enqueues a dispatch job with a 60s delay while queued work remains.
     This smooths throughput (WhatsApp protection). sendDelivery resolves body from
     plain text or the linked approved template, increments template usage, links the
     created MessageLog row to the delivery (campaignDeliveryId) and bumps campaign
     counters.
   - Delivery tracking: per-recipient statuses queued -> sent -> delivered -> read plus
     failed (with error) and skipped (cancel). The inbound webhook statuses handler now
     syncs delivered/read back onto CampaignDelivery rows and the parent campaign counters
     via syncDeliveryFromStatus (guards duplicates so counters stay accurate).
   - Starting a campaign replaces prior deliveries; cancel marks queued ones skipped.
     completeCampaign re-arms recurring campaigns as SCHEDULED.
   - Admin routes: CRUD (merge, guarded by assertEditable for RUNNING/CANCELLED), /stats,
     /audience/preview, /:id/start|pause|resume|cancel (audit-logged), /:id/deliveries
     (status + phone filters, pagination), /:id/export CSV.
   - Admin UI: /admin/campaigns (stat cards, create form with audience preview & template
     picker, lifecycle row actions, list pagination) and /admin/campaigns/[id] (detail,
     delivery progress bar, per-recipient table with status pills + phone search + filters,
     CSV export, start/pause/resume/cancel).

3. WHATSAPP TEMPLATE MANAGEMENT & META APPROVAL WORKFLOW
   Extended MessageTemplate (variables, usageCount, metaTemplateName, metaStatus,
   metaRejectionReason, submittedAt, metaUpdatedAt, waTemplateId + Campaign relation) and
   apps/api/src/services/template.service.ts.
   - validateTemplate: snake_case name <=100, header <=60, body <=1024, footer <=60 and no
     variables, 0-3 buttons title <=20, variables {{N}} contiguous from {{1}},
     numeric-only-header warning. POST /templates/validate returns validation + Meta
     payload preview (previewTemplatePayload).
   - Submit-to-Meta is best-effort: when a WhatsApp Business token + business account ID
     are configured it POSTs real components to the Graph API (
     /{v}/{WABA_ID}/message_templates). Success marks the template APPROVED with the remote
     id; any failure (or no credentials) records locally as SUBMITTED with a warning and
     lets the admin complete it from the Meta dashboard or set the Meta status manually.
   - markTemplateMetaStatus lets admins reflect PENDING/APPROVED/REJECTED (with a
     rejection reason) /PAUSED/DISABLED/IN_APPEAL and consistently maps those back to the
     local status (APPROVED, REJECTED, SUBMITTED).
   - GET /templates/stats (counts per status + totalUsage); GET /templates now also
     returns _count.campaigns; usageCount increments on every outbound send that uses a
     template (campaign + regular sends).
   - Admin UI: Templates tab gained a stats row (total/approved/pending/total usage),
     per-row "Submit to Meta" action, a Meta-status select (Approve/Reject/Pending), meta
     status + rejection-reason pills, and a Uses column (with linked campaigns).

4. REVENUE / MONETIZATION LEDGER
   New RevenueLedger model and apps/api/src/services/revenue.ts.
   - AUTO rows: recordVerifiedRevenue runs from the existing MonetizationGate verify flow
     (monetization.ts) — idempotent per gate (one row), computes revenueAmount from
     monetization.revenuePerVerification and payoutAmount from payoutRate and stores the
     provider/share/session/user references. Pending -> confirmed -> paid lifecycle.
   - MANUAL rows: addManualLedgerEntry for adjustments/refunds/credits (amount, payout,
     currency, provider reference, notes, optional provider/session/user links and status).
   - Settings: monetization.revenuePerVerification (0.25), monetization.payoutRate (0.5),
     monetization.currency (USD) read via updateRevenueSettings / getRevenueSettings and
     surfaced in a settings form.
   - Backfill: backfillRevenueFromEvents replays historical VERIFICATION_SUCCESS
     MonetizationEvents into AUTO rows (used when the ledger is first enabled).
   - Stats + list + CSV export with date/status filters; status update endpoint validates
     transitions. Mounted at /api/admin/revenue/* behind requireAuth; every mutation is
     audit-logged.
   - Admin UI: /admin/revenue page (settings form, revenue/payout/pending/paid stat cards,
     manual entry card, ledger table with date/status filters, per-row status select,
     backfill button, CSV export).
