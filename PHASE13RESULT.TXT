1. GOAL
--------------------------------------------------------------------------------
Reintroduce a provider-AGNOSTIC advertising/monetization system so 400QUES can
serve ads from DIFFERENT advertising providers without being tied to a single
one. The platform depends on an AD PROVIDER INTERFACE, not on any specific
provider (no hard-coded Adsterra/PropellerAds/Google/etc. implementation).
Admins configure providers and assign them to placements without code changes.

Scope is strictly monetization: AD PROVIDERS + AD PLACEMENTS + AD DELIVERY +
AD EVENTS + MONETIZATION INTEGRATION + REVENUE ATTRIBUTION + SIMPLE ADMIN
MANAGEMENT. Campaign management, marketing automation, badges, leaderboards,
public profiles, user accounts, broadcasts, and internal ad-creative
management are NOT restored.

--------------------------------------------------------------------------------
2. CRITICAL ARCHITECTURAL RULE
--------------------------------------------------------------------------------
Application code (game, contribution, WhatsApp, website, analytics) interacts
ONLY with the AdAdapter interface. Individual providers are adapters in a
registry selected by the provider's stored "type". Adding a provider later
requires: (1) creating its adapter, (2) registering it, (3) configuring it in
admin. It does NOT require rewriting game/contribution/WhatsApp/monetization
logic, public pages, or analytics.

--------------------------------------------------------------------------------
3. PROVIDER TYPES (ADAPTER LAYER)
--------------------------------------------------------------------------------
Generic provider types (capability model, extensible):
  SCRIPT         raw HTML/JS tag injected inline
  DIRECT_LINK    plain sponsored destination URL
  REDIRECT       step/redirect to an external destination
  SNIPPET        self-contained inline HTML snippet
  API            provider endpoint (no-op fetch in build-only; fallback HTML)
  CPA            cost-per-action; drives conversion/verification, then credits
  VERIFICATION   unlocks an in-app verification gate
  OTHER          passthrough with verbatim configuration

Each adapter exposes: render(provider, placement, placementCtx),
validateCallback (token/HMAC-SHA256, optional), validateConfig

--------------------------------------------------------------------------------
4. ADAPTER ARCHITECTURE — apps/api/src/services/ad-providers/
--------------------------------------------------------------------------------
types.ts      AdProviderTypes, AdPlacements (keys), AdEventTypes, AdProviderRecord,
              AdAdapter, RenderResult, PlacementContext, CallbackInput,
              CallbackValidation, PlacementServeResult, ConfigCheckResult.
registry.ts   Generic adapters per provider type; getAdapter(type) factory,
              supportedTypes(), providerServesPlacement(record, placement),
              shared validateBySecret (token / HMAC-SHA256 of raw body),
              HMAC + escape helpers. New provider types are added here only.
serve.ts      servePlacement(placement, limit) driven by the AdPlacement table:
                - honors the global monetization.enabled switch
                - serves enabled placements assigned to enabled, non-archived
                  providers
                - priority / random rotation (from settings)
                - records an IMPRESSION event with provider + placement
                - passes per-placement ctx (providerPlacementId, format) so a
                  placement can override the destination/zone/link
                - returns public-safe renders (never credentials)
callbacks.ts  handleProviderCallback(providerId, input): 404 if missing/archived,
              adapter.validate, record CALLBACK event, dedupe via
              processedEvent (key "ad-callback:{providerId}:{eventType}:{ref}",
              P2002 safe), and for CONVERSION/VERIFICATION postbacks promotes
              pending ESTIMATED ledger rows to confirmed.
index.ts      Barrel.

--------------------------------------------------------------------------------
Existing models reused: AdProvider, AdSnippet, MonetizationGate,
MonetizationEvent, RevenueLedger.

AdPlacement (NEW — dedicated placement-management model):
  id, key (unique, e.g. WEB_CONTRIBUTION / WHATSAPP_VERIFICATION),
  name?, description?,
  providerId -> AdProvider (onDelete: SetNull),            provider assignment
  providerPlacementId?   (provider zone/slot/destination/link)
  format?               (capability; defaults to provider type)
  enabled, priority, createdAt, updatedAt
  relations: AdProvider.placementAssignments AdPlacement[]

MonetizationEvent already carries providerId + placement attribution.

--------------------------------------------------------------------------------
7. AD EVENT TRACKING
--------------------------------------------------------------------------------
Generic events: IMPRESSION, CLICK, CONVERSION, VERIFICATION, CALLBACK (+ other
string types permitted). Events are attributable to provider, placement,
provider event/reference id, session, gate, timestamp, and metadata. The
browser-reported IMPRESSION/CLICK/CONVERSION endpoints are idempotent per
event id. Anonymous users stay anonymous (no personal info collected).

--------------------------------------------------------------------------------
8. REVENUE INTEGRATION
--------------------------------------------------------------------------------
Existing RevenueLedger is preserved as the source of confirmed revenue.
recordProviderChannelRevenue attributes ESTIMATED revenue for CPM impressions
and CPC clicks (clearly marked isEstimated=true); CPA/FIXED rely on
verification / validated conversion callbacks. Confirmed revenue is only
promoted from pending estimated rows via callbacks — never fabricated from an
impression/click. Provider-agnostic: no provider-specific rate is hard-coded.

--------------------------------------------------------------------------------
9. WHATSAPP MONETIZATION INTEGRATION (REQUIREMENT 10)
--------------------------------------------------------------------------------
The WhatsApp game/bot flow is UNCHANGED. The verification gate remains the
core monetization flow. selectAdsForGate now resolves the gate's provider
through the generic system: it prefers a provider assigned to a
WHATSAPP_VERIFICATION/GATE placement in the AdPlacement table, else falls back
to the default provider / a provider that serves the GATE placement. The
provider is replaceable without changing game logic.

11. SECURITY DECISIONS
--------------------------------------------------------------------------------
- Provider credentials/configuration stored server-side (AdProvider.configuration).
- Public endpoints, placement/event endpoints, browser components, and
  analytics never return secrets (redactConfig masks secret keys).
- Admin responses redact secrets (redactProvider).
- Provider callbacks validated via token / HMAC-SHA256 and made idempotent.
- test-config validates without leaking secrets.
- All admin provider/placement mutations write audit-log records.
- Deployment-level credentials should live in env vars; DB configuration only
  for provider-specific configurable values. No credentials are committed.
